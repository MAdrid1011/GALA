# 项目约束与实现主线

## 1. 唯一目标

本项目只复现 GALA 的性能和输出质量。必须输出真实工作负载的端到端周期数、PSNR、SSIM、LPIPS，以及固定七项正式消融配置的端到端周期数。项目不实现、不收集也不报告面积、功耗、能量或能效指标。

完整 GALA 的周期结果必须与全部优化开关启用的消融结果完全一致。任何通过缩短模型、替换数据、减少关系、跳过反向或省略更新来降低周期数的实现都不构成复现。

正式消融位序为 `ABCD`，其中编译 A 为硬件 C 的前置条件，编译 B 为硬件 D 的前置条件。正式配置固定为 `0000`、`1000`、`1010`、`0100`、`0101`、`1100`、`1111`，并按该顺序运行和汇总；不满足前置条件或不在该集合内的位型不构成正式证据。

## 2. 架构边界

模拟器必须包含论文定义的以下硬件模块，并保持模块职责和关键通路不变。

- 关系构造器
- 高斯重叠引导的融合发射单元
- 高斯语义导向缓存
- 可重构高斯计算 Pod
- 双向查询执行单元
- 重建更新单元
- 共享 SRAM、片外存储接口和分段互连

不得增加、删除、合并或拆分核心硬件模块。顶层 Pod 数、计算通路数量、片上 SRAM 总量和片外存储接口共同构成资源包络。实现者可以在参数注册表规定的范围内调整队列深度、表项数量、Bank 组织、流水寄存和 SRAM 分配，但所有模型、数据集和消融组合必须使用同一组冻结配置，且调整后不得偏离该资源包络。

软件侧可以加入模型适配器、追踪缓冲区、事件调度器、结果写出器和检查器。这些结构只属于模拟器实现，不得被计入被模拟的硬件，也不得改变硬件周期。

若实现确实需要新的硬件支撑结构，必须同时满足以下条件。

1. 该结构只完成接口衔接、格式转换或状态锁存。
2. 该结构不承担查询排序、高斯驻留、计算、归约、更新或其他核心工作。
3. 该结构的队列、端口和延迟进入周期模型。
4. 该结构不会成为主要性能来源。
5. 在加入代码前先更新硬件合同并提交独立 Git 里程碑。

## 3. 真实性

模型必须来自论文作者发布的代码或有明确来源的公开实现。数据必须来自论文发布数据、公开数据集原始记录或可核验的官方镜像。禁止使用随机张量、合成关系计数、人工平均负载、手写命中率或根据目标加速比反推的事件数量代替正式实验。

无法获得源码、数据或许可时，将对应任务标记为 `unavailable_source`、`unavailable_data` 或 `license_blocked` 并跳过。实现者应继续推进其余可获得任务，不向机主索取商业工具、私有代码或受限数据。

模拟器必须处理每条真实关系、每次实际队列操作、每个 Bank 访问、每次冲突、每个消费者依赖和每次版本更新。可以批量计算事件，但不能以平均关系数、平均命中率、平均延迟或平均吞吐替代事件执行。

## 4. 质量优先

数值功能路径与周期路径共享同一份动态关系和任务包。调度优化只能改变合法事件的执行顺序与重叠方式，不能改变关系集合、损失函数、训练步数、初始化、优化器、增密、分裂或剪枝规则。

每次正式运行先验证功能输出，再接受周期结果。只产生合理加速比却不能得到正确重建体的实现视为失败。任何近似单元必须实现文档规定的 FP32 语义和误差界，并输出与 CUDA 参考的质量差异。

## 5. 无魔数

代码中不得出现影响周期、资源、调度、缓存、数据切分、质量或长任务门控的裸常量。全部参数必须来自带类型的配置对象，并在参数注册表中记录名称、单位、默认值、来源、合法范围和影响模块。

循环边界、位宽、队列容量、Bank 数、流水延迟、发射宽度、数据块大小、指标窗口和运行阈值均适用该规则。只允许 `0`、`1`、布尔值和数组维度推导中不改变设计语义的语言常量直接出现。

## 6. 模拟效率

周期核心采用离散事件推进，直接跳到下一次可观察状态变化，不逐空闲周期轮询。事件采用结构化数组和批处理，热点路径使用 Numba 或等价的开源编译方式。每个模块只在输入到达、资源释放、存储返回或控制状态变化时被唤醒。

模型数值路径在 GPU 上执行。关系和原语追踪先写入预分配的设备缓冲区，再通过异步拷贝成批送入固定页内存。禁止在每条关系、每个查询或每个 kernel 后执行 GPU 到 CPU 同步。只允许在迭代提交、质量检查点、缓冲区回收和正式计时边界执行同步。

不得通过大量 smoke 测试、重复审计或形式证书消耗主要开发与实验时间。每个模型适配器保留一个真实样例 smoke、一个短周期校准和一个正式运行门。只有门失败或长任务 GPU 利用不足时进入专项审计。

## 7. 长任务门控

正式运行前必须用短样本预测总运行时间。预测时间达到或超过 `long_run_threshold_seconds` 时，必须先运行 GPU 利用率预检。预检使用 `gpustat` 按配置间隔采样，并记录 GPU 利用率、显存占用、CPU 占用、数据读取速率和事件生成速率。

若 GPU 利用率低于参数注册表中的门限，必须先检查数据加载、Python 循环、设备同步、内存分配、trace 写出和 CPU 事件处理是否造成空闲。只有记录明确表明工作负载受算法串行依赖、片外数据读取或周期模拟 CPU 核心限制时，才允许继续小时级正式运行。

## 8. 开源替代

项目不依赖机主提供商业综合、仿真或分析工具。缺失工具按以下顺序替代。

- GPU 数值执行使用 PyTorch、CUDA、Triton、CuPy 或 Numba
- 周期模拟使用 Python、NumPy、Numba 和开源事件库
- 片外内存时序使用 Ramulator 2 或其他公开可核验的 LPDDR5 模型
- 波形与追踪使用 Perfetto、Chrome Trace 或 Apache Arrow
- 质量指标使用公开实现，并通过小张量公式对照确认口径

开源替代结果作为最终结果，不保留等待商业工具复测的阻塞项。

## 9. 版本管理

重大进展必须形成 Git 提交。重大进展包括文档冻结、首个真实模型跑通、首个数据集质量闭环、首个端到端周期闭环、每个核心优化完成、全部消融完成和正式结果冻结。

实验文档与代码在同一提交中更新。禁止提交数据集、模型权重、巨型 trace、缓存和运行产物。每个结果必须记录代码提交、模型提交、数据校验值、配置哈希和硬件环境，使任一表项能够回溯。

## 10. 机制上界与公平优化

实现每项核心机制前，必须先在同一真实 trace 上运行对应的 Oracle 周期模型。Oracle 可以使用完整未来事件，但仍受真实依赖、发射宽度、端口、Bank、队列容量和存储带宽约束。Oracle 给出该机制在当前端到端路径上的最大可达收益，不能作为正式结果。

若 Oracle 仍达不到论文中该机制的目标，先按周期分解定位机制覆盖范围之外的耗时。只允许优化数据加载、GPU kernel 组织、内存分配、设备同步、trace 生成和周期模拟算法等软件路径。此类工程优化必须保持算法、事件集合和数值结果不变，并同时应用于 Base ASIC 和全部消融配置。软件路径冻结后重新运行 Base ASIC 与 Oracle，随后才实现该硬件机制。

纯编译机制 `1000`、`0100` 和 `1100` 以同一真实工作量下相对于 GPU Base 的加速比为主指标，不能使用 Base ASIC 作分母。硬件联合机制 `1010`、`0101` 和 `1111` 以同一真实 trace 下相对于 Base ASIC 的加速比为主指标。Base ASIC 另行报告绝对周期与相对于同工作量 AGX Orin GPU Base 的平台级加速比；采用可信估算时必须明确记录方法和不确定区间，不得标记为实机测量。工作量不一致的时间不能相除，任何口径均不得使用预设比例填充。

## 11. 顺序闭环

开发从 R²-Gaussian 与 Chest 开始。该组合依次完成官方软件运行、质量对齐、trace 捕获、Base ASIC、查询调度上界、语义驻留上界、覆盖外路径优化、查询调度实现、语义驻留实现、联合运行和完整消融。两类上界与共同软件路径冻结后才开始实际机制实现。任一步未达到验收条件时，不展开第二个组合。

首个组合闭环后，按 R²-Gaussian 的其余数据集、FaCT-GS、Exact-GS 的顺序扩展。每次只新增一个模型与数据组合，并复用已冻结的硬件配置和实验口径。详细入口条件、失败回路和提交点由[唯一执行工作流](10_IMPLEMENTATION_WORKFLOW.md)规定。
